# Uni-VOC 챗봇 (웹 버전)

시나리오1(장학추천) + 시나리오2(복수전공 자격확인) **통합 챗봇** 데모용. 브라우저에서 카톡처럼 쓰는 채팅창 하나(`/`) + 직원 승인 화면(`/staff`) + 관리자 페이지(`/admin`, API 키 설정·장학금 자료 추가)로 구성됨.

- **한 채팅창(`/`) 안에서 장학금/복수전공 두 시나리오를 자유롭게 오갈 수 있음.** 학생이 URL이나 탭을 고를 필요 없이, 첫 메시지를 보면 AI가 어떤 상담인지 스스로 판단해서(키워드 우선, 애매하면 LLM 분류, 그래도 애매하면 직접 물어봄) 알맞은 흐름으로 들어감. 대화 중간에 "근데 복수전공은 어떻게 돼?"처럼 화제를 바꾸면 자동으로 전환되고, 각 시나리오의 진행 상황(예: 장학금 골라놓은 것, 복수전공 자격판정 결과)은 서로 안 섞이고 각자 보관돼서 전환했다 돌아와도 안 날아감. (예전 버전은 `/`(장학금)과 `/dualmajor`(복수전공)가 따로 있었는데, 지금은 `/dualmajor`가 `/`로 리다이렉트만 함 — 옛날 북마크 호환용.)
- **시나리오1 — 장학금 매칭**: 넓고 자유로운 대화형 매칭. 학생이 조건을 말하면 규칙 기반으로 후보를 걸러줌.
- **시나리오2 — 복수전공 깔때기** (`/staff`에서 직원 승인): "복수전공 가능한가요?"에서 시작해 실제 HITL(직원 승인) 워크플로우까지 이어지는 2단계 데모.
  - **1단계 — 자격요건 즉시판정**: 재학상태/이수학기/수료학점/제외학과 4가지를 그 자리에서 확인. **판정(가능/불가능)은 LLM이 절대 하지 않고 `rules.py`의 결정론적 규칙만 계산한다.**
  - **2단계 — 이수과목 인정신청서 자동 초안 + 직원 승인**: 자격 충족 학생이 "이미 들은 과목 인정받고 싶어"라고 하면, AI가 과목을 자연어로 받아 `curriculum.py`의 실제 교육과정표(원문 대조 완료, 데모 조합: **미래자동차공학과 → 컴퓨터공학전공**)와 학수번호 완전일치로 대조해 신청서 초안을 만듦 — **이 매칭도 LLM이 아니라 결정론적 규칙만 판단.** 학생이 제출하면 `/staff` 화면에서 직원이 근거(매칭된 학수번호·과목명·인정 사유)를 보고 승인/반려하는 게 진짜 HITL 지점.
  - 두 단계 모두 공통 설계 원칙: LLM은 (a) 자연어 슬롯/과목 추출, (b) 이미 계산된 결과를 친근하게 설명 — 이 두 역할만 맡고, 실제 판단(자격여부/과목인정여부)은 항상 사람이 짠 규칙이나 사람(직원)이 함. 돈/졸업요건에 영향 주는 판단이라 AI가 혼자 결정하지 않는다는 설계 원칙. 라우팅(어느 시나리오인지 판단)이 늘었다고 이 원칙이 바뀌는 건 아님 — 라우팅도 애매하면 추측 안 하고 직접 물어봄.

## 폴더 구조

```
UNIVOC/
├── schemas.py       # 데이터 구조 정의 (건드릴 필요 없음)
├── matching.py       # 장학금 매칭 로직 (규칙 기반 1차 필터, 시나리오1)
├── rules.py            # 복수전공 자격요건 판정 로직 (결정론적, LLM 미사용, 시나리오2-1단계)
├── curriculum.py       # 학과별 교육과정표 데이터 + 이수과목 인정 매칭 로직 (결정론적, LLM 미사용, 시나리오2-2단계)
├── bot_core.py        # 대화 로직 + RAG 자료 구조화 (Gemini 호출)
├── config.py          # API 키/모델 설정 읽기·쓰기
├── app.py              # 웹 서버 (FastAPI)
├── bulk_ingest.py       # 크롤링 공지(.md) 폴더 전체를 한 번에 DB에 채워넣는 CLI (로컬 전용)
├── scholar_rag_database/  # 크롤링해둔 장학금 공지 원문(.md) — bulk_ingest.py가 읽는 소스
├── static/
│   ├── index.html      # 학생용 채팅 화면 (통합 — 장학금 + 복수전공/이수과목 인정, 한 세션 안에서 자동 전환)
│   ├── staff.html        # 직원 승인 화면 (이수과목 인정신청서 승인/반려, HITL)
│   ├── admin.html       # 관리자 화면 (API 키 등록 + RAG 자료 추가/삭제)
│   └── assets/           # 영남대학교 로고/심볼 (yu-logo.png, yu-mark.png)
├── data/
│   ├── scholarship_db.json           # 실제 장학금 DB (처음엔 비어있음, 관리자 페이지에서 채움)
│   ├── recognition_applications.json  # 이수과목 인정신청서 저장소 (제출 시 자동 생성)
│   └── config.json                    # API 키 저장 위치 (관리자 페이지에서 자동 생성됨)
├── requirements.txt
└── README.md
```

## 1. 설치

```bash
cd UNIVOC
python3 -m venv venv
source venv/bin/activate        # 윈도우는 venv\Scripts\Activate.ps1
pip install -r requirements.txt
```

## 2. 실행

```bash
python3 app.py
```

터미널에 `Uvicorn running on http://127.0.0.1:8000` 뜨면 성공. 브라우저에서 아래 주소 열면 됨:

- **학생용 채팅 (장학금 + 복수전공/이수과목 인정, 통합)**: http://localhost:8000
- **관리자 페이지**: http://localhost:8000/admin
- **직원 승인 화면 (이수과목 인정신청서 HITL)**: http://localhost:8000/staff

화면들 모두 상단 네비게이션으로 서로 이동 가능함. (`/dualmajor`는 예전 링크 호환용으로 남겨뒀고 접속하면 `/`로 자동 이동함.)

### 시연 순서 (예시 대사)

같은 채팅창 하나에서 이어짐 — 학생은 아무 탭도 고를 필요 없음.

1. `/`에서 아무 말이나 시작 (예: "안녕") → AI가 장학금/복수전공 중 뭐가 궁금한지 되물음
2. "나 미래자동차공학과 3학기째고 45학점 들었는데 컴퓨터공학전공 복수전공 가능해?" → 키워드로 바로 복수전공 모드 진입, 즉시 자격요건 판정(초록 배너)
3. "이수과목 인정받기" 버튼 클릭 (또는 "이미 들은 과목 인정받고 싶어") → AI가 이수과목 물어봄
4. "취업/현장기술세미나(AME057) 들었어" 하고 "다 말했어" → AI가 교육과정표 대조해서 인정 가능 과목 정리, 제출 여부 확인
5. "제출" → 신청서 접수, 직원 승인 대기 상태로 전환
6. (선택) 같은 창에서 "나 장학금도 궁금한데" 하면 장학금 모드로 자동 전환 — 복수전공 진행상황은 그대로 보관됨
7. `/staff`로 이동 → 방금 제출된 신청서가 "승인대기" 탭에 뜸, 매칭 근거(학수번호·과목명·"타전공인정 미래자동차공학과") 확인 후 승인/반려

> 참고: 2단계 데모는 지금 "미래자동차공학과 → 컴퓨터공학전공" 조합만 실제 이수지침 PDF 원문과 대조해서 구축해놨음 (`curriculum.py`). 이 조합의 AME057(취업/현장기술세미나)은 컴퓨터공학전공 교육과정표에 실제로 "타전공인정 미래자동차공학과"로 공식 편성돼 있는 진짜 사례라서 가짜 데이터가 아님. 다른 학과 조합은 아직 데이터가 없어서 물어보면 AI가 "데모 범위 밖"이라고 정직하게 안내함.

## 3. API 키 등록 (터미널 안 써도 됨)

이전 버전은 터미널에서 `export GEMINI_API_KEY=...` 해야 했는데, 이번 버전은 **관리자 페이지에서 붙여넣고 저장 버튼만 누르면 됨.** 서버 재시작 필요 없이 바로 반영됨.

(환경변수 `GEMINI_API_KEY`를 설정해두면 그게 항상 우선 적용됨 — 둘 다 필요 없고 편한 쪽 하나만 쓰면 됨.)

모델명도 같은 화면에서 바꿀 수 있음 (기본값 `gemini-2.5-flash`). 나중에 모델명이 바뀌거나 404 에러 나면 여기서 최신 모델명으로 교체.

## 4. 장학금 자료(RAG) 추가하기 — 크롤링한 공지 붙여넣기

관리자 페이지 "2. 장학금 공지 추가" 섹션에서:

1. 크롤링해둔 공지 원문(마크다운/텍스트)을 텍스트박스에 붙여넣거나, `📎 파일에서 불러오기`로 `.md`/`.txt` 파일 선택
2. **"AI로 분석하기"** 클릭 → Gemini가 구조화한 결과가 미리보기로 뜸 (아직 저장 안 됨)
3. 내용 확인하고 **"이 내용으로 저장"** 클릭 → `data/scholarship_db.json`에 실제로 추가됨

여러 개 공지를 추가하고 싶으면 이 과정을 반복하면 됨. 잘못 들어간 항목은 아래 "3. 현재 등록된 장학금" 표에서 삭제 버튼으로 지울 수 있음.

> 서버를 껐다 켜도 `data/scholarship_db.json`에 저장된 내용은 그대로 남아있음 (파일 기반 저장이라서).

### 4-1. 한 번에 왕창 추가하기 — `bulk_ingest.py`

크롤링해둔 공지 파일이 `scholar_rag_database/` 폴더처럼 여러 개(.md) 있으면, 관리자 페이지에서
하나씩 붙여넣는 대신 터미널에서 한 번에 처리할 수 있음:

```bash
python3 bulk_ingest.py                    # scholar_rag_database/ 폴더 전체 처리 (기본값)
python3 bulk_ingest.py 다른/폴더/경로        # 다른 폴더를 쓰고 싶으면
```

- 관리자 페이지가 쓰는 것과 **완전히 같은** 추출 로직(`bot_core.extract_scholarship`)을 그대로 재사용함 — 별도 로직 아님.
- 이미 DB에 이름이 같은 공지가 있으면 자동으로 건너뜀 → 여러 번 실행해도 중복 안 생김. 그래서 새로 크롤링한 파일만 폴더에 추가하고 다시 돌려도 안전함.
- 한 건 처리될 때마다 바로 `data/scholarship_db.json`에 저장하니, 72개 중 중간에 하나가 실패해도 그 전까지 처리된 건 안 날아감. 실패한 파일은 마지막에 목록으로 알려줌.
- **반드시 로컬(내 컴퓨터)에서 돌려야 함.** Gemini API를 실제로 호출하는 작업이라 네트워크가 제한된 환경(클라우드 샌드박스 등)에서는 안 됨.

## 4-2. 장학금 매칭 정확도 개선 (2차 소프트매칭)

실제 크롤링 DB(68건)를 조사해보니, 신청 가능한 41건 **전부**가 `special_conditions`(특례조건)를
공지 원문 그대로의 자유텍스트로 갖고 있었음(예: "국민기초생활 수급자 우대", "본인 또는 부모가
대전 거주 1년 이상"). 예전 버전은 이걸 학생이 입력한 텍스트와 정확히 문자열이 같아야만
매칭되는 방식이라, 사실상 거의 항상 걸러져서 **있는 장학금도 "매칭되는 게 없다"고 나오는
버그**가 있었음. 재학상태도 마찬가지로 "재학"(학생이 캐주얼하게 말한 것) vs "재학생"(공지
원문 표현)처럼 워딩이 조금만 달라도 정확일치라 튕겨나갔음.

지금은 2단계로 나눠서 처리함:
1. **1차 규칙필터(`matching.py`, 결정론적)**: 날짜/신청가능여부, 재학상태(부분포함 매칭으로
   워딩 차이 허용), 평점(수치 비교), 학자금지원구간(수치 비교)만 여기서 거름.
2. **2차 소프트매칭(`bot_core.soft_match_conditions`, LLM 보조판단)**: 특례조건/학과제한/학년조건처럼
   자유텍스트라 정확매칭이 불가능한 것만, 1차를 통과한 후보에 한해서 LLM한테 "학생 상황이랑
   이 조건이 맞는지" 판단하게 함. **애매하면 절대 배제하지 않고 무조건 후보에 남기게 강제**함
   (장학금은 후보 탐색이지 최종 확정이 아니라서, 있는 걸 못 보여주는 게 없는 걸 보여주는 것보다
   훨씬 나쁘다고 판단함). "우대"라고 적힌 조건도 필수요건이 아니라 가산요소로 취급해서 배제하지
   않음. 이 LLM 호출이 실패해도 1차 필터 결과는 그대로 살아남아서 검색 자체가 막히지 않음.

실제 DB로 검증한 결과: 재학·3.5학점·3구간·특별조건 없음인 평범한 학생 기준으로 **예전 로직은
매칭 0건, 새 로직은 1차 필터만으로 15건**이 후보로 남음(2차 소프트매칭 거치면 더 정리됨).

추가로 `SlotState`의 필수 슬롯에 `major`(학과)·`grade_or_semester`(학년/학기)도 넣어서 항상
물어보게 했음 — DB 조사해보니 학년/학기 조건이 있는 공지가 68%(28/41건)나 됐는데 예전엔 아예
안 물어봐서 매칭에 못 썼었음. 슬롯 추출 프롬프트도 "애매한 답변에서 값을 추측하지 말고 다시
구체적으로 물어봐라"로 강화해서, 학생이 두루뭉술하게 답하면 AI가 그냥 넘어가지 않고 예시를 들어
다시 되묻게 만듦.

## 5. 지금 이 버전의 한계

- **로컬 1인용 서버임.** `localhost:8000`은 내 컴퓨터 안에서만 열림. 여러 명이 동시에 접속하려면 같은 와이파이/네트워크 안에서 내 컴퓨터 IP로 접속하거나, 별도 서버 호스팅이 필요함. 세션은 사람마다(브라우저마다) 구분되게 만들어놨으니 여러 명이 동시에 써도 대화가 안 섞임.
- **서버 재시작하면 대화 세션은 초기화됨.** (장학금 DB, API 키, 인정신청서는 파일로 저장되니까 안 사라짐.)
- **이수과목 인정신청 2단계는 딱 한 학과 조합("미래자동차공학과 → 컴퓨터공학전공")만 지원함.** 다른 조합을 물어보면 AI가 데모 범위 밖이라고 정직하게 안내하고 진행 안 함. 다른 조합을 추가하려면 이수지침 PDF에서 해당 학과 페이지를 찾아 `curriculum.py`에 같은 형식으로 옮기면 됨.
- **직원 승인(`/staff`)은 로그인/권한 구분이 없는 데모용 화면임.** 실제 배포 시엔 수업학적팀 계정 인증이 붙어야 함.
- **복수전공 판정·인정 로직에 들어간 규정/교육과정표는 2026학년도 1학기 공지·이수지침 PDF 기준 수동 반영값임.** 학기가 바뀌거나 학사 서버 연동 전까지는 `rules.py`/`curriculum.py`를 사람이 직접 최신화해야 함.
- **AI 분석 결과는 100% 정확하다고 보장 못 함.** 그래서 장학금 RAG 자료는 "분석 → 미리보기 확인 → 저장"으로 한 단계 끊어놨음. 복수전공 판정·이수과목 매칭은 애초에 AI가 판정하지 않고 규칙 기반(학수번호 완전일치)으로만 계산하니 이 문제에서 자유로움 — LLM은 슬롯/과목 추출, 설명 문구 생성에만 관여.

## 6. 자주 만나는 에러

| 에러 | 원인 | 해결 |
| --- | --- | --- |
| "Gemini API 키가 설정되지 않았어요" | 아직 관리자 페이지에서 키 저장 안 함 | `/admin`에서 키 입력 후 저장 |
| `404 model not found` | 모델명이 바뀜 | 관리자 페이지에서 최신 모델명으로 교체 |
| `ModuleNotFoundError` | 가상환경 활성화 안 하고 설치했거나 설치 자체를 안 함 | `pip install -r requirements.txt` 다시 |
| 매칭 결과가 항상 0개 | DB에 `is_open_application: true`인 장학금이 없음 | 관리자 페이지에서 최신 공지 추가 |
